# Яндекс Вебмастер API

`ywm.py` отдаёт сырые данные API Вебмастера: агенту не нужно писать свой клиент
под каждый вопрос. Оценок «хорошо или плохо» в скрипте нет. Он скачивает,
постранично обходит выдачу, сводит дни в итоги и пишет CSV. Выводы делаешь ты.

## Запуск

```
pip install -r requirements.txt     # один раз, нужен только requests
python ywm.py <команда> --host example.com ...
```

`--host` принимает домен, URL или host_id (`https:example.com:443`). Скрипт найдёт
сайт в аккаунте и выберет главное зеркало. Если ошибка про `YANDEX_WEBMASTER_TOKEN`
или 401, значит, токен не настроен или истёк (живёт 6 месяцев). Пройди с
пользователем [SETUP.md](SETUP.md): часть шагов он делает в браузере сам.

Общие флаги: `--csv FILE` сохраняет все строки в UTF-8 с BOM, чтобы Excel не ломал кириллицу
(в pandas — `encoding="utf-8-sig"`); `--limit` ограничивает только консоль;
`--refresh` идёт мимо кэша. Каждый ответ API кэшируется в `cache/` до конца дня. Повторный
вопрос бесплатен, а оборванная длинная выгрузка при повторе докачивает только недостающие
страницы. Кэш за прошлые дни удаляется сам.

## Сначала выбери источник

У Яндекса нет одного метода, как Search Analytics у Google. Есть несколько источников
с разной глубиной, и вопрос надо сразу отнести к одному из них.

| Вопрос | Команда | Глубина | Чего не умеет |
|---|---|---|---|
| Показы, клики, CTR, позиции сайта целиком; сравнение месяцев | `totals` | по дням с 2020 | нет разбивки по запросам и страницам |
| Запросы или страницы с цифрами, спрос, фильтры по тексту, адресу, региону, устройству | `qa` | **только последние 14 дней** | история глубже; у крупного сайта хвост обрезан |
| Запросы одной страницы, страницы одного запроса, с кем конкурирует страница, каннибализация | `qa --url-equals`, `qa --group url --query-equals`, `pairs --page`, `pairs` | 14 дней | то же |
| Топ запросов за прошлую неделю или месяц, динамика одного запроса | `popular`, `query-history` | ~85 дней до последнего дня с данными | только топ до 3000, хвоста нет |
| Запрос × страница × регион за полтора года | `pro-export` | 550 дней | бесплатно 100 «URL × день» в сутки, готовится до суток |
| Что выпало из поиска и почему | `samples --kind events` | события с причинами, глубина зависит от сайта | выборка, не полный список |
| Все страницы сайта со статусом в поиске, canonical, кодом | `archive` | снимок, отстаёт на недели | свежих выпадений может не быть |
| Динамика страниц в поиске, обхода, ИКС, ссылок | `history --kind ...` | с 2018–2020 | — |
| Внешние и битые внутренние ссылки | `samples --kind external-links / broken-links` | — | выборка, до 50 000 |
| Проблемы сайта, важные страницы, sitemap | `diagnostics`, `important-urls`, `sitemaps` | — | — |
| Переобход страниц и sitemap | `recrawl`, `sitemap-recrawl` | — | тратят квоту, см. ниже |
| Всё остальное: фиды, владельцы, подтверждение прав, добавление сайта или sitemap | `raw` + [reference.md](reference.md) | — | — |

Частый тупик: «сравни запросы или страницы за октябрь и ноябрь». Бесплатный API так не
умеет, `qa` видит только 14 дней. Что делать:
- сайт целиком — `totals` за два одинаковых отрезка (неполный месяц сравнивай с тем же
  числом дней прошлого: 1–20 с 1–20);
- запросы — `popular` за каждый период, если оба попадают в его глубину (только топ);
- отдельные страницы — `pro-export` по этим URL. Сначала запусти его без `--yes`: сухой
  прогон бесплатен и считает расход. Потом спроси пользователя, например: «Сравнить
  запросы по 3 главным страницам за 1–14 октября и 1–14 ноября? Это 84 из 100
  бесплатных URL-дней на сегодня, выгрузка готовится от 20 минут до нескольких часов».
Скажи пользователю об ограничении прямо, а не подменяй вопрос молча.

## Свежесть: проверяй первой

```
python ywm.py freshness --host example.com
```

У каждого источника своя последняя дата. Окно `qa` отстаёт на 2–6 дней, итоги
сайта — на ~3 дня, PRO — на ~2 дня. После сбоя у Яндекса в октябре 2026 часть источников
застыла: на 23.11.2026 `popular` и история обхода заканчивались 07–10.10. Прежде чем
говорить «за последнюю неделю», посмотри, какая неделя есть на самом деле, и назови в
ответе реальные даты.

## Команды

### Сайты и сводка
```
python ywm.py hosts                     # главные зеркала; --all — все, включая http и www
python ywm.py summary --host example.com   # ИКС, страниц в поиске и исключено, число проблем
```

### totals — итоги сайта по дням (search-queries/all/history)
```
python ywm.py totals --host example.com --start 2025-01-01 --end 2026-11-20 --by month
python ywm.py totals --host example.com --start 2026-10-01 --end 2026-11-20 --device MOBILE_AND_TABLET --csv t.csv
```
Колонки: shows, clicks, ctr (%), avg_show_position, avg_click_position. `--by day|week|month`:
суммы, позиции взвешены по показам и кликам. Хвостовые дни с нулями (данных ещё нет)
скрипт отбрасывает и пишет об этом. Длинный период режется на куски по году.

### qa — запросы или страницы за 14 дней (query-analytics/list)
```
python ywm.py qa --host example.com                                  # топ-5000 запросов по показам
python ywm.py qa --host example.com --group url --max-rows 0 --csv pages.csv
python ywm.py qa --host example.com --url-equals https://example.com/blog/post/    # запросы страницы
python ywm.py qa --host example.com --group url --query-equals "купить диван"      # страницы запроса
python ywm.py qa --host example.com --query-contains диван --query-not-contains икеа --region 1
python ywm.py qa --host example.com --min-position 4 --max-position 15 --min-impressions 50   # точки роста
python ywm.py qa --host example.com --url-contains blog/ --day 2026-11-10 --by-date
```
- Колонки: impressions, clicks, ctr, position (средняя с весом по показам), demand (спрос,
  только для запросов), days (дней с показами), top_partner (самая частая страница для
  запроса или самый частый запрос для страницы), у `--group url` ещё full_url.
  top_partner считается по всему сайту даже с фильтром по адресу. Если в выгрузке
  страницы X у запроса top_partner — другая страница, значит, по этому запросу она
  показывается чаще X. Это первый признак конкуренции; подробно — `pairs --page`.
- Позиция — средняя за 14 дней, а не снимок выдачи. В «точки роста» по позиции 4–15
  попадает много хвоста с единичными показами, поэтому ставь порог по показам или спросу.
  Пороги (какая позиция — точка роста, сколько показов заметно, какая доля чужой страницы —
  конкуренция) задаёт пользователь, скилл их не знает. Не спросил — выбери сам и назови
  их в ответе.
- Фильтры (`--query-*`, `--url-*`, повторяемые, объединяются через И) идут в API. Числовые
  `--min-*/--max-*` (impressions, clicks, ctr, position, demand) отбирают строки после
  суммирования за окно.
- `--min-impressions N` к тому же останавливает скачивание: API сортирует по показам за окно,
  и ниже порога строк уже не будет. Для хвоста крупного сайта это 5 вызовов вместо 300.
  «Скачано 2500 из 150 000, остановлено по --min-impressions» — так и должно быть, это
  не потеря.
- `--max-rows` по умолчанию 5000, `0` — все (потолок ~150 000).
- `--by-date` даёт строку на ключ × день. `--day D` оставляет ключи с показами в день D.
  Цифры при этом за все 14 дней, а с `--by-date` остаётся только строка дня D.
- `--region ID` (повторяемый), `--device`, `--location` (по умолчанию API считает
  органику `WEB_LOCATION`; `ALL_LOCATIONS` добавляет динамические места Директа).
  Справочник регионов: `pro-info --regions`.
- Без фильтров выводится строка «Покрытие»: какая доля показов и кликов сайта за окно
  попала в скачанное.

### pairs — с кем конкурирует страница, матрица запрос × страница
```
python ywm.py pairs --host example.com --page https://example.com/blog/post/ --top-queries 100
python ywm.py pairs --host example.com --top-urls 50 --csv pairs.csv --groups-csv cannibal.csv
python ywm.py pairs --host example.com --urls-file urls.txt --min-urls 2
```
- `--page X` отвечает на вопрос «где эта страница конкурирует с другими страницами сайта».
  Берёт `--top-queries` главных запросов X и раскладывает каждый по всем страницам сайта:
  вызов на запрос. В колонке page_share доля X в показах запроса, в all_urls — страницы с
  показами и позициями.
- `--url`, `--urls-file`, `--top-urls` строят матрицу по заданному набору страниц: вызов на
  страницу. Пары видны только между страницами набора, поэтому для одной страницы
  используй `--page`. В файле — полные URL или пути, по одному в строке.
- Цифры пары относятся именно к этой странице. В консоли — запросы с показами на
  ≥ `--min-urls` страницах: число страниц, суммы, главная страница и её доля.
- `--csv` — все пары, по строке на «страница × запрос» (url, query, impressions, clicks, ctr,
  position, demand, days); считай по нему. `--groups-csv` — список из консоли, где all_urls —
  склеенная для чтения строка `путь (показы, поз. X) | ...`.

### popular и query-history — топ запросов и динамика запроса
```
python ywm.py popular --host example.com --start 2026-09-01 --end 2026-09-30 --order-by clicks
python ywm.py query-history --host example.com --query "купить диван" --start 2026-08-01 --end 2026-10-07
python ywm.py query-history --host example.com --query-id a08b... --start ... --end ...
```
Есть любой период внутри глубины, включая один день. Показатели: показы, клики, средняя
позиция показа и клика. Пустой ответ обычно значит «нет данных за эти дни», а не «нет
показов»: сверь с `freshness`. В истории запроса дни без данных заполнены нулями.

### pro-export и pro-status — запрос × URL × регион за 550 дней
```
python ywm.py pro-info --host example.com                       # лимит на сегодня и доступные даты
python ywm.py pro-export --host example.com --path /blog/post/ --start 2026-10-01 --end 2026-10-31
python ywm.py pro-export ... --yes                              # запуск после согласия пользователя
python ywm.py pro-status --host example.com --wait 60 --out pro.csv
```
Цена — «URL × день»: одна страница за месяц стоит 30 из 100 бесплатных в сутки на домен
(сброс в 00:00 МСК). Сухой прогон (без `--yes`) ничего не тратит: он сверяет даты с
доступными, считает расход, сравнивает его с остатком лимита и делит работу на задачи.
Запускай его, чтобы назвать пользователю цену. `--path` — только точные адреса, маски
раздела нет. Для раздела сначала собери список страниц (`qa --group url --url-contains`,
`archive`) и выбери главные. Готовится офлайн 20 мин – 2 ч, бывает до суток. Долгое
ожидание `pro-status --wait` запускай в фоне. Строка результата = день × страница × запрос ×
регион. Сырые `.csv.gz` сохраняются рядом с `--out`, потому что ссылка живёт 24 часа.
Потолка 150 000 у PRO нет: это единственный способ увидеть весь хвост запросов страницы.
Создание выгрузки бывает недоступно: 23.11.2026 POST на всех сайтах сразу отвечал
`504 Gateway time out` с пустым телом, и с российского, и с зарубежного адреса, а
`pro-info` работал. Лимит при этом не тратится,
это видно по `pro-info`. Скажи пользователю и повтори позже, не в цикле.

### Индексирование
```
python ywm.py archive --host example.com --out pages.csv          # все страницы: код, статус, canonical, title
python ywm.py samples --host example.com --kind events --event removed --csv removed.csv
python ywm.py samples --host example.com --kind events --reason NOT_CANONICAL --since 2026-11-01
python ywm.py samples --host example.com --kind in-search --url-contains blog/
python ywm.py history --host example.com --kind in-search --start 2026-01-01 --end 2026-11-23
python ywm.py important-urls --host example.com                 # список задаётся только в интерфейсе
python ywm.py diagnostics --host example.com                    # --all — все проверки
python ywm.py sitemaps --host example.com                       # --parent ID — дочерние, --user-added
```
- **«Что выпало и почему»** — `samples --kind events --event removed --since ДАТА`
  («за две недели» — сегодня минус 14 дней). Это самые свежие данные с причиной и
  target_url (куда редирект или canonical). Чтобы оценить потери, склей с
  `qa --group url --max-rows 0` по full_url: там показы и клики страниц. Окно `qa`
  кончается раньше последних событий, поэтому у страницы, которой в `qa` нет, показов
  в этом окне не было (0). Число событий в `history --kind events` и в `samples` за ту же
  дату может немного расходиться (выборка), адреса и причины бери из `samples`.
- **«Все страницы и их статус»** — `archive`: один файл на все известные Яндексу страницы.
  Колонки: url, httpCode, status (SEARCHABLE или причина исключения), lastAccess,
  redirTarget, relCanonical, title, metaDescription, плюс сводка по статусам. Это
  снимок, и он отстаёт. На проверенном сайте последний обход в архиве был на 17 дней
  старше сегодня, а 23 из 57 страниц, выпавших по событиям, в архиве ещё числились в
  поиске. Свежие выпадения бери из событий, архив — для структуры: noindex, canonical,
  редиректы по разделам.
- **Сколько страниц в поиске.** `summary` (текущий счётчик), `history --kind in-search`
  (точки на обновлениях базы) и `samples --kind in-search` (список) дают разные числа:
  на одном сайте 1170, 1140 и 1184. Для числа бери `summary`, для динамики — `history`,
  для адресов — `samples`. Расхождение назови.
- **Сколько страниц вне поиска.** `summary` даёт только число исключённых, без причин
  (на одном сайте 179). Не-SEARCHABLE строк в `archive` больше (там же 382): в архиве
  все известные адреса, включая редиректы, canonical-дубли и адреса с параметрами. Какие
  статусы входят в счётчик `summary`, документация не говорит. Причины бери из `archive`
  по разделам, число из `summary`, и назови оба.

`history --kind`: `in-search`, `events` (появились и выпали), `crawl` (обход по HTTP-кодам),
`sqi` (ИКС), `broken-links`, `external-links`. `samples --kind`: `in-search`, `events`, `crawl`,
`external-links`, `broken-links` (`--indicator SITE_ERROR|DISALLOWED_BY_USER|UNSUPPORTED_BY_ROBOT`).
Причины исключения — в [reference.md](reference.md#причины-исключения).

### Переобход
```
python ywm.py recrawl --host example.com                        # квота и очередь
python ywm.py recrawl --host example.com --url /page/ --url /page2/   # сухой прогон
python ywm.py sitemap-recrawl --host example.com                # лимит приоритетного переобхода
```

### raw — любой метод
```
python ywm.py raw GET H/owners --host example.com
python ywm.py raw GET H/search-urls/in-search/samples --host example.com --param offset=0 --param limit=100
python ywm.py raw POST H/query-analytics/list --host example.com --body @body.json
python ywm.py raw GET U/hosts
```
`H/...` — путь сайта, `U/...` — путь пользователя, иначе путь от корня (`v4/...`, `v4.1/...`).
Методы, параметры и enum'ы — в [reference.md](reference.md).

## Что тратит квоту или меняет данные

По умолчанию эти команды делают сухой прогон: показывают, что и сколько потратят.
Реальный запуск — тот же вызов с `--yes`, и только когда пользователь сам об этом попросил:

- `recrawl --url ... --yes` — суточная квота переобхода сайта (у разных сайтов от десятков до
  ~1500 URL);
- `sitemap-recrawl --id ... --yes` — 10 раз в месяц на сайт;
- `pro-export ... --yes` — бесплатные URL-дни; `--paid` (платный тариф, деньги владельца) —
  только по прямому указанию;
- `raw POST/DELETE ... --yes` — добавление и удаление сайтов, sitemap, фидов, подтверждение
  прав. Для части этих методов нужен доступ `webmaster:verify`, которого у токена может не
  быть: тогда API вернёт 403.

`archive` и все остальные команды только читают.

## Ловушки

### 14 дней qa и смысл фильтров
- У `query-analytics` нет параметра дат: окно — последние 14 дней с данными, и оно сдвигается
  каждый день. Свою историю «запрос × страница» можно накопить, только выгружая каждый день.
- `--stat-filter FIELD:OP:VALUE[:FROM:TO]` проверяет условие **на каждый день** диапазона, а
  не на сумму за окно. `IMPRESSIONS gt 5` оставит запросы, у которых больше 5 показов в
  каждый из дней. Для порога по сумме бери `--min-impressions`. Без `FROM:TO` скрипт
  подставляет всё окно. Даты вне окна (и `--day` вне окна) API отвергает с ошибкой
  `RESTRICTIONS_VIOLATED`.
- Набор строк пересчитывается для каждого окна. Запрос, державшийся в топе за счёт
  выпавшего дня, исчезает вместе с показами за остальные дни.

### Потолок 150 000 и хвост
- На окно API отдаёт не больше ~150 000 уникальных запросов, отсортированных по показам.
  Ни один фильтр (текст, URL, устройство, регион) не достаёт запросы за потолком. На одном
  крупном сайте набор покрывал 54% показов и 47% кликов. Смотри строку «Покрытие» и
  `totals`; полный хвост страницы есть только в `pro-export`.
- У сайтов ниже потолка хвост виден целиком и весит много. На одном сайте (148 тыс.
  запросов за 14 дней) запросы с одним показом дали 39% кликов. Порог «от 2 показов»
  выкинул бы их. Google такие запросы прячет, Яндекс нет.

### Адреса, спрос, позиции
- В `qa` адрес страницы — путь (`/blog/post/`), в остальных методах — полный URL. Для
  стыковки бери колонку full_url. `--url-equals` сравнивает побуквенно, поэтому `/page` и
  `/page/` — разные адреса.
- DEMAND — сколько раз запрос вообще задавали (по Яндексу, не по сайту). У страниц он 0.
  Показов может быть больше спроса: так бывает, когда сайт стоит в выдаче дважды.
- CTR везде в процентах. POSITION за день может отсутствовать. В `totals` и `popular` две
  позиции: средняя позиция показа и средняя позиция клика, это разные метрики. Смешивать
  их с позицией Google нельзя.
- `--location ALL_LOCATIONS` включает показы на динамических местах Директа, поэтому
  показов больше. Для сравнения с Google оставляй органику (по умолчанию).
- Регионы `--region` — субъекты: 1 — «Москва и Московская область», 10174 — «Санкт-Петербург
  и Ленинградская область», 225 — Россия. Город Москва (213) даёт 0. Беларусь есть только
  на уровне страны. Разреза по регионам нет: каждый регион — отдельная выгрузка.

### Нули и пустые ответы
- `totals` за дни без данных отдаёт нули, а не пропуски (скрипт отбрасывает хвостовые).
  `query-history` заполняет нулями весь период. `popular` за дни без данных молча
  возвращает пустой список.
- `samples` — выборки, а не полные списки, до 50 000 строк. `count` бывает завышен: API
  отдаёт меньше строк, чем обещал, и скрипт пишет об этом.
- События индекса и история страниц в поиске приходят срезами, на обновлениях поисковой
  базы, раз в несколько дней. «Последние две недели» могут оказаться двумя датами событий.
  Глубина `samples --kind events` зависит от сайта.
- У отдельных запросов кликов больше, чем показов (CTR выше 100%). Так отдаёт API, это не
  ошибка скрипта. В выводах такие строки отмечай.
- `samples --kind crawl` (indexing/samples) на многих сайтах рвёт соединение, а
  отвечая, отдаёт старые обходы. Для состояния страниц используй `archive`.
- В `archive` названия статусов свои: `META_NO_INDEX` и `BAD_QUALITY` вместо `NO_INDEX` и
  `LOW_QUALITY` из API, дата lastAccess в виде `ДД.ММ.ГГГГ`. По документации в архиве
  только страницы из Sitemap. На проверенном сайте там были и редиректы, и noindex, и
  canonical-дубли: 1 375 строк при 319 адресах в sitemap.

### Сайты и лимиты
- http, https и www — отдельные хосты; у неглавных зеркал заполнен main_mirror.
- `qa` — 10 000 вызовов в час **на домен**. Разные сайты не делят лимит. `--workers` до 8;
  при 429 скрипт ждёт и повторяет, скачанные страницы остаются в кэше.
- Выгрузка больше ~50 вызовов (`qa --max-rows 0` у крупного сайта, `pairs` по сотням страниц,
  `samples` на десятки тысяч) идёт минутами. Запускай её в фоне. Если оборвётся, повтори тот
  же вызов: в тот же день он продолжит из кэша.

### Git Bash и ведущий `/`
Git Bash превращает аргумент `/blog/` в `C:/Program Files/Git/blog/`. Для адресов скрипт
это исправляет сам. Пиши адреса без ведущего слеша (`blog/post/`) или полным URL. Для
остальных значений с `/` используй `MSYS_NO_PATHCONV=1 python ywm.py ...`.
